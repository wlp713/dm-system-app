# DM 系统 v0.1 架构与后续扩展

## 当前范围

首版交付一条最短现场路径：**选择车间和班次 → 4M 或两小时检查 → 判断正常/异常 → 拍照 → 保存 → 查看记录**。LOSS 台账、会议行动和复杂检查项暂缓，防止在工厂口径未统一前把表单做复杂。

4M 的四个上层维度固定为人、机、料、法。此版各维度只有一张通用打卡表；车间专属子项以后由配置驱动。人员照片可选；机、料、法以及两小时检查照片必填；异常说明必填。

## 操作路径与界面

- 底部固定四个入口：工作台、点检、记录、我的。
- 工作台只显示当前车间和班次、当天 4M 完成数、当前两小时检查状态、本班记录数，以及 4M / 两小时检查两个快捷入口。
- 点检页再分为 4M 与两小时检查；4M 页列出人、机、料、法四个大类，再进入统一打卡表。
- 打卡表在同一张卡片内依次处理结果、照片、说明和提交。异常时说明必填；人员照片可选，其他点检要求照片。
- 视觉使用蓝色工作台、白色信息卡片和蓝 / 青两种快捷操作色，移动端优先；图标分别使用 iOS 与 Android 原生符号，网页使用稳定的文字图标回退。

## 代码层次

| 目录 | 职责 |
| --- | --- |
| `src/app` | Android、iOS、网页共用的页面与导航 |
| `src/ui` | 卡片、照片控件、统一点检表单与视觉规则 |
| `src/domain` | 点检记录、时间段、车间与中泰文案 |
| `src/data` | 仓储接口、本机存储与照片文件持久化 |
| `src/state` | 当前使用人、车间、记录的界面状态 |
| `site` | 安装下载页与网页演示入口 |

页面不直接调用存储 API。`CheckRepository` 定义读写边界，当前 `localRepository` 使用 AsyncStorage。原生照片复制到应用文档目录，网页演示版使用浏览器存储。

## 数据规则

- `CheckRecord` 含唯一 ID、类型、4M 维度、车间、人员、班次、结果、说明、照片 URI、时段键和提交时间。
- 每次提交产生新记录，不覆盖历史；页面按当前车间和时段显示最新结果。
- 4M 时段键为本地日期加班次。两小时时段目前按本地时钟 00:00、02:00……22:00 分段。工厂班次与检查窗口确认后，应改为后端可配置的排程。
- 记录与照片目前只存在同一台设备或浏览器，卸载应用或清除浏览器数据会使本机数据不可用。

## Firebase 接入顺序

1. 建立同一个 Firebase 项目，Android 与 iOS 使用各自应用标识接入同一后端。配置 Firebase Auth、Firestore、Storage 与访问规则。
2. 引入 `FirebaseCheckRepository`，用 Firestore 存放结构化记录、Storage 存放照片。先上传照片得到存储路径，再创建记录，记录与照片都有同一 ID。
3. 用 Firestore 实时监听更新 `DmProvider`，使安卓与苹果读取同一份服务端记录。离线时将提交标为待同步，恢复连接后重试并防重。
4. 加入车间范围权限、服务器时间、标准版本、照片保留策略和审计记录。车间专属点检子项由配置表驱动。

上线前须确认账号来源、各车间点检标准、具体班次时间、两小时排程及泰文术语。以上业务配置不会改变已有的 4M 上层结构。

## 安装交付

Android 演示 APK 从 GitHub 构建环境产生。正式版需固定生产签名和发行渠道。iPhone 现在可将网页演示版添加到主屏幕；原生版通过 Apple Developer 签名后用 TestFlight 或 App Store 分发。下载页只在实际链接存在时启用对应原生按钮。
